# 0002: Accept a bounded runtime model profile

Accepted 2026-09-05 for the next deterministic experiment only. BG-052 reviews the [runtime specification](../specs/RUNTIME-V0.md); BG-017 supplies the [test strategy](../specs/TEST-STRATEGY.md). Production architecture, native transport and host process ownership remain unselected.

## Review and resolutions

| Ambiguity / counterexample | Accepted resolution |
| --- | --- |
| A provider launched under a started milestone survives an operation deadline while a notified-ready consumer remains blocked | Lifecycle initialization is tracked independently of operation milestone completion. A notified-ready provider retains its startup deadline even if a weaker dependent is already admitted. A provider whose declared milestone is started may not supply notified-ready evidence in this initial profile |
| A provider exhausts retries; an after-only consumer waits forever for an attempt that never launched | An activation attempt has a terminal scheduling outcome even when blocked/rejected before launch. After opens on that outcome; requires remains unsatisfied |
| A provider-only stop changes desired state before discovering an out-of-scope consumer | Validate the stop closure before any mutation. Rejected requests preserve desired state, readiness, retry timers and budgets |
| A consumer is starting, or waiting for retry, when its provider is stopped | Stop-scope checks cover active desired-running consumers (starting/running/retry-pending), not just running processes. Blocked queued consumers in the same operation must also be cancelled or included; an unrelated operation conflicts |
| A successful one-shot is rerun by an unrelated start and repeats irreversible work | Activation session means one fixed graph revision within the manager epoch, not one CLI call. Reuse successful completed evidence in that session. Explicit stop invalidates it; a later start deliberately reruns it. No automatic one-shot retry |
| Startup deadline cancels a provider already used by a successful consumer | Initial cancellation stops every still-initializing generation owned by the operation, even if started evidence admitted a consumer. The consumer remains running with dependency loss, per R-07. Report partial outcome; no hidden cascade or rollback |
| Operation failure leaves retry ownership unclear | A successful activation transfers retry policy to desired-running service state. Deadline/cancellation suppresses retries for unfinished participants; a later explicit start is required. Provider-loss blocks waiting consumers only until their original operation terminates |
| A stop arrives while launch is in flight, and a late completion starts a new worker | Superseded operation closes admission immediately but retains launch ownership. Late completions are stopped/reclaimed; generation identity prevents them joining a replacement |
| Restart cannot tell whether a completed one-shot counts as running | Initial restart accepts only an owned live long-running generation. A one-shot or absent service rejects restart without side effects; use explicit stop/start for a deliberate one-shot rerun |

These are manual counterexample traces and semantic resolutions, not executed model checks. R-01–R-18 with their clarifications are accepted for a deterministic model; they remain candidate requirements for a real runtime. There is no proof that all interleavings are consistent yet.

## Next experiment

Implement a pure, in-memory Python 3.11+ model using standard-library unittest. Python is host-only test tooling, already used in this repository; it adds no target dependency and does not select the init language. A compiled host supervisor now would conflate policy validation with process/transport uncertainty. A formal model checker could explore broader state spaces, but defer the extra language/tool dependency until bounded trace exploration demonstrates a need.

Model effects explicitly: request launch, request stop, request reclaim and publish observation. Tests inject the corresponding completion/failure events; the model must not immediately pretend every effect succeeds. No subprocess, socket, shell, filesystem mutation or native syscall belongs in this first model. Assert state and emitted effects against hand-authored expected outcomes, not expectations generated by the same implementation.

Initial model limits: at most 8 services, 16 edges, 2 automatic replacements per service, 64 retained diagnostic records and 256 externally supplied events per trace. Exceeding a limit must reject input before unbounded work. Use integer synthetic time and explicit positive deadlines/delays; a tick jump processes overdue deadlines without giving them fresh budgets. Exhaustively permute batches of at most 4 independent input observations with fixed precedence before dispatch; do not claim this explores all possible system interleavings.

A model batch is a manager observation cut: accept already-available terminal/stop/deadline evidence before readiness/admission effects. Events arriving in later cuts cannot retroactively prevent an already-dispatched consumer; they produce dependency loss instead. Include both kinds of trace. This avoids claiming that a user-space manager knows about a failure it has not yet observed.

Record elapsed time and peak memory with interpreter/platform metadata on a fixed 8-service graph and 1,000 repeated traces. These are baseline measurements, not product performance thresholds. Terminate a model test run after 30 seconds in the harness; record a timeout as failure, never a pass. Functional bounds above are acceptance requirements; runtime performance targets will follow measurement.

BG-053 implements the model and failure matrix. BG-054 owns portable host/CI fixtures, including real child and shell checks. BG-050 request transport, BG-040 readiness transport and BG-028 real ownership must be accepted before a host supervisor. No additional Aether change is needed for the model; native readiness and general service launch remain gated.
